# 渲染管线

这篇描述渲染上下文、布料网格与顶点同步、织物材质、光源与环境、显示模式、路径追踪与相机的实现。代码在 `src/render/`，视口侧的循环与监听在 `src/ui/viewport3D/`。

同一份场景有两条出图路径：光栅化负责交互中的即时帧，WebGPU 路径追踪负责静止时的收敛图像，两者共用 `THREE.Scene`、相机与光源。

章节顺序依次为：渲染上下文（§1）、布料网格与顶点同步（§2）、织物材质（§3）、光源与环境（§4）、显示模式（§5）、光线追踪（§6）、相机与拾取（§7）、性能策略（§8）。

## 1. 渲染上下文

上下文是两条渲染路径的共同底座：一次建立 renderer、场景、两台相机与控制器。

### 1.1 建立与释放

`createRendererContext(canvas)`（`render/renderer/rendererContext.ts`）一次建齐两条渲染路径共用的对象：

```typescript
interface RendererContext {
  renderer: THREE.WebGPURenderer;          // antialias、alpha:false、pixelRatio ≤ 2
  scene: THREE.Scene;                      // background = FALLBACK_BACKGROUND，含舞台地面
  camera: ViewportCamera;                  // 当前生效的相机（下面两台之一）
  perspectiveCamera: THREE.PerspectiveCamera;   // 45° fov，near 0.1 / far 100
  orthographicCamera: THREE.OrthographicCamera; // 半深度 ORTHO_CLIP_RANGE = 100
  projection: CameraProjection;
  orthoViewHeight: number;                 // zoom = 1 时正交视野的世界高度
  controls: OrbitControls;                 // enableDamping，target = (0, 0.9, 0)
  canvas: HTMLCanvasElement;
  renderMode: RenderMode;
  rayConfig: RayTracingConfig;
  lightConfig?: LightConfig;               // 光源上次是从哪套设置建的
  renderConfig?: RenderConfig;             // 色调映射同上
  rayTracer: RayTracingRenderer | null;    // 懒创建
  rayTracerLoading: Promise<RayTracingRenderer | null> | null;
  rayCapability: RayTracingCapability | null;  // 光追探测结论，首次切换后才有值
  resizeObserver?: ResizeObserver;         // 由 Viewport3D 挂上，dispose 时断开
  disposed: boolean;
}
```

#### 1.1.1 建立顺序

1. 视口被布局隐藏时 `clientWidth/Height` 为 0，宽高各取 `Math.max(1, …)`。
2. `new THREE.WebGPURenderer({ canvas, antialias: true, alpha: false })` → `await renderer.init()` → `setPixelRatio(Math.min(devicePixelRatio, 2))` → `setSize(w, h, false)`。
3. 色调映射先设成 `ACESFilmicToneMapping`、`toneMappingExposure = 1.0`；映射方式随后由 `applyLightConfig()` 按工程写回（§4.5）。
4. `renderer.shadowMap.enabled = false`（§4.4）。
5. 场景背景设为 `FALLBACK_BACKGROUND`，紧接着 `addStageFloor(scene)`（地面长度(m) 20，含参考网格，`renderer/stageFloor.ts`）。
6. 建两台相机与 `OrbitControls`（§7.1），`orthoViewHeight` 取初值 1 后调 `syncOrthoFrustum()` 对齐视锥。

> **注**：曝光固定为 1.0，没有界面入口。

`detectWebGPU()` 是 `navigator.gpu.requestAdapter()` 的封装；不通过时 `Viewport3D` 显示 `#webgpu-error` 并提前结束。它只判断运行环境是否提供 WebGPU，路径追踪能否运行由 `verifyRayTracing()` 在首次切到光线追踪时验证（§5.3）。

#### 1.1.2 释放与重复挂载

StrictMode 与 Fast Refresh 会在同一个 canvas 上再挂一套上下文，因此：

- 初始化 effect 里每个 `await` 之后都要判 `cancelled`，并对已建好的 `RendererContext` 与 `GarmentEngine` 就地释放。
- `disposeRendererContext()` 以 `ctx.disposed` 作防护，重复调用不会二次释放。
- 释放时同时断开 `resizeObserver` 并释放光追实例，包括仍在加载的那个 Promise。

### 1.2 尺寸同步

`resizeRenderer(ctx, w, h)`（`rendererContext.ts`）同步宽高比、绘图缓冲与正交视锥。

尺寸为 0（窗格被隐藏）时直接返回，保留上一次的有效缓冲；`Viewport3D` 用一个挂在容器上的 `ResizeObserver` 转交新尺寸，并把观察器存进 `ctx.resizeObserver`，释放上下文时一并断开。

### 1.3 出图入口

`renderScene(ctx)` 是循环唯一调用的出图函数：

```typescript
export function renderScene(ctx: RendererContext): void {
  // 画面在动时 rayTracer.render() 返回 false，这一帧交给光栅管线显示。
  if (ctx.renderMode === 'raytraced' && ctx.rayTracer?.render(ctx.scene, ctx.camera)) return;
  ctx.renderer.render(ctx.scene, ctx.camera);
}
```

主循环本体（帧序、`await` 链、镜像到 store、隐藏窗格跳过绘制）见 [01-架构总览](./01-架构总览.md) §4.2。

## 2. 布料网格与顶点同步

渲染侧只有一份布料网格挂多个材质槽，顶点每帧由 CPU 回读刷新，正面朝向取决于制版阶段的绕序。

### 2.1 一份网格、多个材质槽

所有版片合成一个 `THREE.Mesh`（`ClothMeshManager`，`render/material/fabricMaterial.ts`）：

| 属性 | 处理 |
| --- | --- |
| `position` / `normal` | `DynamicDrawUsage`，每帧由模拟写入 |
| `uv` / `index` | 静态缓冲，制版阶段确定 |
| `frustumCulled` | `false`：布料形变大 |
| BVH | 表面拾取走 three 内置的 `Raycaster`；`three-mesh-bvh` 的包围树只在光追侧挂到 `BufferGeometry.boundsTree` 上（§6.3.2） |
| geometry groups | 每片一条 `{ start, count, materialIndex }` |

多材质靠 group 而不是多网格：`fabricSlotPlan()` 按 `Panel.fabricId` 去重出材质数组，悬空引用统一落到同一个灰色回退槽（§3.2、§3.4）。

### 2.2 每帧的同步链路

模拟在 GPU compute 里完成，渲染网格是 three 的 `BufferGeometry`，两者之间每帧走一次 CPU 往返：

```
最后一个子步之后，同一个 encoder：
  法线三段（清零 → 按三角形累加 → 归一化，见 04 §2.5）
  copyBufferToBuffer(位置缓冲 → readbackBuf)
  copyBufferToBuffer(法线缓冲 → readbackNormalsBuf)
主线程：
  ClothSimulator.readback() 用 mapAsync 取回 { positions, normals }
  GarmentEngine.stepSimulation() 先扫非有限值，发现 NaN/Inf 就保留上一帧
  ClothMeshManager.updateFromSim(positions, normals) 写进 BufferAttribute、置 needsUpdate、刷新 boundingSphere
```

> **注**：同一份位置数组同时供非有限值检查、缝纫线叠画、PIN 标记与拾取网格使用（04 §3.3、§3.4）。

### 2.3 顶点数据与显示朝向

- 三角形绕序在制版阶段由轮廓逆时针保证，正面朝外；所有布料材质一律 `side: THREE.DoubleSide`，背面法线由 three 内部翻转。
- 求解器写回的是逐粒子面积加权法线（04 §2.5）。
- UV 由 2D 制版坐标按包围盒归一化生成（05 §3.3），供 UV 检查模式的棋盘格、织物贴图的平铺与偏移、以及导出 GLB 的 `uv_0` 使用。

## 3. 织物材质

织物外观由 PBR 加 Sheen 参数表达；一条记录可被多片共用，改动按三种签名决定就地更新还是重建，可见性靠 geometry group 重挂。

### 3.1 创建与就地更新

外观全部使用 three 标准材质，不写自定义 TSL 节点图：

```typescript
// render/material/fabricMaterial.ts
export function createFabricMaterial(app: FabricAppearance, composite?: THREE.Texture | null): THREE.MeshPhysicalMaterial;
/** 就地改写现有实例，材质编辑因此不重建网格。 */
export function applyFabricAppearance(mat: THREE.MeshPhysicalMaterial, app: FabricAppearance, composite?: THREE.Texture | null): void;
```

- `applyFabricAppearance()` 写完 `MeshPhysicalMaterial` 的外观字段后置 `needsUpdate`（字段清单与语义见 02 §6.1）。
- `maps` 的四个槽位写到 `map` / `normalMap` / `roughnessMap` / `metalnessMap`，`uvTiling` / `uvOffset` 写进每张贴图的 `repeat` / `offset`（加载与缓存见 §3.6、字段语义见 02 §6）。
- 有贴图时颜色取白、金属度与粗糙度取 1，通道值由贴图给出；清空槽位后回到底色与标量参数。传入 `composite` 时由合成贴图接管 albedo 槽（颜色固定为白，§3.7）。
- Sheen 采用 Charlie 分布加 Fresnel 近似，与 glTF `KHR_materials_sheen` 一致。

### 3.2 一份记录、多个使用者

`fabricSlotPlan(project, panelIds)` 决定材质数组与每片的槽位，共用同一条记录的多片天然同材质。带可见印花的片改用 `clothMaterialSlotPlan()`，在每条记录之外再按版片拆一个独占槽。

> **注**：单片的改动必须先把它复制为独立记录（使用片数与【复制为独立记录】见 06 §6.6）。

### 3.3 三签名决定重建还是就地改

`GarmentEngine.applyFabrics(project, mode?)` 每次工程变更都被视口调用，它按 `clothSignatures.ts` 的三种签名逐级判断：

| 签名 | 变了会怎样 |
| --- | --- |
| 可见性签名 | `applyPanelVisibility()` 重挂 geometry 分组（§3.5） |
| 材质槽签名 | `bindClothMaterials()` 重新绑定槽位与分组 |
| 逐片外观签名 | 槽位不变时 `applyFabricAppearance()` 就地改写；传入的 `mode` 与当前材质模式不同则先重建材质 |

三份签名一致时函数直接落到物理签名分支且不做事。逐片外观签名同时带上 `printSignature()`（每片可见印花的摆放、平铺、不透明度与图片短键），所以改印花也只走就地路径：重绘该片的合成贴图，不重绑槽位、不重建网格。

### 3.4 一片一材质如何生效

`ClothMeshManager.addGroups()` 给每片写 `{ start, count, materialIndex }`，`setMaterials()` 换整份材质数组。

### 3.5 可见性分组

绑定时记下每片的索引区间（`clothGroupRanges`，`garmentEngine.ts`），`applyPanelVisibility()` 据此重挂分组：

- 隐藏的片没有 group，那段索引不会被绘制；`Mesh.raycast` 按 group 遍历，因此也点不到。
- 粒子仍在模拟，片子再次显示时回到原槽位。
- 隐藏的版片同时不进选中高亮（`syncSelectionOverlay` 过滤）。

### 3.6 贴图的加载与复用

四个贴图槽的加载与释放由 `render/material/fabricTextures.ts` 负责，`applyFabricAppearance()` 只把结果写进材质：

- 数据 URL 交给 `Image` 解码，解码完成才把 `THREE.Texture` 挂到对应槽位并置 `needsUpdate`。
- 同一 URL 的解码结果按 data URL 缓存；每个材质各持一张 `Texture`（共享已解码的图像），各自的 `repeat` / `offset` 互不干扰。最后一个引用释放时缓存条目删除，材质 `dispose` 时一并释放贴图。
- albedo 用 `SRGBColorSpace`，normal / roughness / metallic 用 `NoColorSpace`；四张贴图统一 `RepeatWrapping`，`repeat` 取 `uvTiling`、`offset` 取 `uvOffset`。
- 贴图尚未解码时槽位为空，`exportGLB()` 在写文件前 `await whenFabricTexturesReady()`，不会把空图写进 GLB。

### 3.7 印花合成贴图

带印花的版片每片一张画布贴图（`render/material/printTexture.ts`），底色、花纹与图案合成后写进材质的 albedo 槽：

- 画布像素尺寸按版片网格包围盒的厘米长宽比算出，长边 1024、短边最少 64；`CanvasTexture` 用 `SRGBColorSpace`。
- 绘制顺序固定：先铺 `baseColor`，再把 `maps.albedo` 按 `uvTiling` / `uvOffset` 平铺一遍（每轴最多 32 块），最后按 `Print` 顺序画图案。
- `printPlacement()` 把摆放换算进 UV 方格：中心以轮廓包围盒中心（不含缝份）为原点，再除以网格包围盒的尺寸；矩形按 `repeat` 分格铺图，绕中心逆时针旋转 `angleDeg`，以 `opacity` 叠加。
- 图案超出网格包围盒的部分留在画布外，由版片 UV 自然裁掉。
- 图片解码是异步的：首次绘制未完成的图案留空，解码完成后回调重绘并置 `needsUpdate`；失败或超过 8 MB 的图片不会重试。
- 这张贴图由 `GarmentEngine` 按版片缓存（`printTextures`），没有可见印花的片在重绑槽位时释放；释放时连同 `CanvasTexture` 一起 `dispose`。

`exportGLB()` 导出当前材质，印花合成贴图因此作为基础色贴图随 GLB 内嵌。

### 3.8 明线叠画

明线是叠在布料之上的独立线段，不是材质：

- `topstitchSegments()`（`core/engine/topstitchThreads.ts`）逐片取出可见明线，用 `topstitchRows()` 得到每一行的采样折线；每个采样点吸附到该片网格里最近的顶点，再加上该片的 `vertexOffset` 换成一整份合并网格里的粒子索引，相邻重复点合并成一段。
- `TopstitchThreads` 把这些段建成一个 `LineSegments`：位置与顶点色两个缓冲，材质是 `vertexColors` + 透明 + 关深度写入，`renderOrder = 4` 让它压在布料表面之上。
- 模拟每帧回读位置后调用 `update(positions)` 覆写线段两端；重建布局后索引可能暂时越界，那些段落在原点隐藏。
- 布料网格重建或明线记录变化时整体 `attach()` 重建线段；`setVisible()` 跟随布料显隐。

> **注**：明线只在视口里叠画，不进布料网格、不参与碰撞与导出；辅料同样没有 3D 实体（02 §4.3）。

### 3.9 模特皮肤

人体材质独立于织物，由 `render/material/bodyMaterial.ts` 的 `applyBodySkin(root, appearance)` 就地写入：

- 无贴图的人体材质在首帧换成 `MeshPhysicalMaterial`，颜色、粗糙度与 clearcoat 取 `Avatar.appearance`（缺省 `DEFAULT_SKIN_APPEARANCE`，字段语义见 02 §7.1）。
- 皮肤高光用物理材质的 clearcoat 表达，因此发生一次 `MeshStandardMaterial → MeshPhysicalMaterial` 的替换；同一源材质被多个网格共用时只替换一次，其后的改动只写字段。
- 材质名匹配 `eye` / `lash` / `brow` 的细节材质，以及带 albedo 贴图或非 PBR 的材质保持原样。
- `AvatarStage.applyAppearance()` 以 `JSON(appearance)` 为签名跳过重复写入，因此改肤色只重写材质，不重建模特、布料与模拟（06 §2）。

## 4. 光源与环境

一盏工程灯对应一个 three 光源对象，面积光需要额外装载 LTC 近似贴图，环境图有独立的强度出口与生命周期；阴影只在光追里出现，色调映射直接设在渲染器上。

### 4.1 一盏灯对应一个 three 光源对象

```typescript
export function applyLightConfig(ctx: RendererContext, cfg: LightConfig, render: RenderConfig): void {
  const group = ensureLightGroup(ctx.scene);      // scene.getObjectByName('sceneLights')
  clearGroup(group);
  group.add(new THREE.AmbientLight(0xffffff, iblStrength(cfg) * 0.15));
  ctx.scene.environmentIntensity = iblStrength(cfg);
  for (const light of normalizeLights(cfg)) {
    const object = lightToObject(light);          // null = 该类型暂不支持（面积光等 LTC）
    object.name = light.name;
    object.visible = light.enabled;               // 关掉的灯留在场景里，只是不进 traverseVisible
    group.add(object);
    if (object.target) group.add(object.target);   // 目标点也入场景，矩阵才会更新
  }
  // renderer.toneMapping ← aces / reinhard / linear / none
  ctx.rayTracer?.invalidateLights();
  ctx.rayTracer?.invalidateEnvironment();
}
```

| `SceneLight.type` | three 光源 | 读取的字段 |
| --- | --- | --- |
| `directional` | `DirectionalLight` | `position` 定入射方向、`target` 定朝向 |
| `point` | `PointLight(color, intensity, distance, decay 2)` | `position`、`distance` |
| `spot` | `SpotLight(…, coneAngleDeg→弧度, penumbra, decay 2)` | `position`、`target`、`distance`、锥角、边缘 |
| `area` | `RectAreaLight(color, intensity, width, height)` + `lookAt(target)` | `position`、`target`、`width`、`height` |

光源列表来自工程数据，场景树的【光源】集合是同一份列表；`EngineSync` 按整份光源列表的签名变化调用本函数，新增、删除、改名、开关都只改列表，一次操作都可撤销。

### 4.2 面积光的 LTC 支持

`RectAreaLight` 需要三层的 LTC 近似贴图：

- 列表里第一次出现面积光时 `installAreaLightSupport()` 异步 `import('three/examples/jsm/lights/RectAreaLightTexturesLib.js')` 并 `RectAreaLightNode.setLTC(...)`，装好后重新调用一次 `applyLightConfig`。
- 这张数据模块不进主包，未使用面积光时不加载。
- 装载失败只记一条警告；装载完成前，面积光被 `lightToObject` 跳过。

### 4.3 环境贴图

```typescript
// render/renderer/sceneEnvironment.ts
export const DEFAULT_ENV_URL = '/env/royal_esplanade_1k.hdr';
export const FALLBACK_BACKGROUND = new THREE.Color(0x2a2a2e);
/** 按扩展名选 RGBELoader / EXRLoader / TextureLoader；同一 url 只保留一张贴图。 */
export async function applySceneEnvironment(scene, url, filename = url): Promise<boolean>;
/** 释放不再选中的环境贴图；若正是当前环境，同时退回 FALLBACK_BACKGROUND。 */
export function releaseSceneEnvironment(scene, url): void;
```

- 内置环境图只有一张（CC0 室外全景，署名见 `assets/env/ATTRIBUTION.md`），工程未指定环境时使用它。用户可导入 `.hdr` / `.exr` / `.png` / `.jpg` / `.jpeg` / `.webp`，导入件存进 IndexedDB 后由 object url 提供；非 hdr/exr 走 `TextureLoader` 并标 `SRGBColorSpace`。
- 环境光的有效强度由 `iblStrength(lights)` 给出，关闭时为 0。它写进 `scene.environmentIntensity`，并按 `iblStrength × 0.15` 叠一盏 `AmbientLight`；`EnvironmentStage.apply()` 与 `applyLightConfig()` 都读它。
- object url 与贴图的生灭由 `core/engine/environmentStage.ts` 管理（`apply` / `release`）；环境图数据与导入记录在工程命令层（06 §5.4），换图的撤销重做走工程历史。`EngineSync` 只在换了哪一张环境图时重新加载贴图，改强度或开关只走光源重建。

### 4.4 阴影

光栅化路径没有阴影：`shadowMap.enabled = false`，`SceneLight` 没有 `castShadow` 字段；布料网格设了 `castShadow = receiveShadow = true`，因此没有投影。

> **注**：光线追踪不复用这套设置。路径追踪器重新收集场景光源（`getLights` 走 `traverseVisible`），通过次级光线计算遮挡，关掉的灯不参与。

### 4.5 色调映射

没有独立的后处理节点管线，色调映射直接设在渲染器上，由 `applyLightConfig()` 按 `render.toneMapping` 选择：

| 工程取值 | 渲染器设置 |
| --- | --- |
| `aces` | `ACESFilmicToneMapping` |
| `reinhard` | `ReinhardToneMapping` |
| `linear` | `LinearToneMapping` |
| `none` | `NoToneMapping` |

SSAO、Bloom 之类屏幕空间效果未接入（§8 待完成清单）。

## 5. 显示模式

显示模式的生效值只有一个来源，它决定同一份场景使用哪一组材质；切到光追是懒加载，运行期失败则复位成光栅化。

### 5.1 两个来源，一个生效值

| 来源 | 何时读 | 是否随工程保存 |
| --- | --- | --- |
| `project.scene.render.mode` | 建布料网格时读一次（`GarmentEngine.createRenderMesh()`） | 字段在工程里，界面切换不写回 |
| `uiStore.renderMode` | 每次变化都调 `engine.applyFabrics(project, renderMode)` | 存进偏好，不写回工程 |

两者取值集合相同（`prefs.ts` 白名单含全部六个 `RenderMode`），运行时只由 UI store 决定（分工见 02 §8.2.1）。

### 5.2 模式与材质的对应

`createMaterialForMode(app, mode)`（`fabricMaterial.ts`）：

| mode | 实现 |
| --- | --- |
| `shaded` | `createFabricMaterial()`：`MeshPhysicalMaterial` + sheen + `DoubleSide` |
| `raytraced` | 同一份织物材质，随后由 BVH 路径追踪器读取并渐进采样 |
| `wireframe` | `MeshBasicMaterial({ color: 0x66ccff, wireframe: true, side: DoubleSide })` |
| `uvCheck` | 16×16 棋盘写进 `DataTexture`，由 `MeshBasicMaterial`（`DoubleSide`）采样 |
| `normalVis` | `MeshBasicNodeMaterial`（`DoubleSide`、`toneMapped: false`）：`packNormalToRGB(normalLocal.normalize())` 打包后做 sRGB 反解，得到物体空间法线的颜色 |
| `shadedWireframe` | `switch` 落到 `shaded` 分支，返回同一份织物材质 |

界面的三项入口共用同一份显示模式值：

- 显示模式列表（`ui/optionTables.ts` 的 `DISPLAY_MODES`）在五个渲染模式后追加【合身热图】【应变热图】。
- 3D 工具条【显示】下拉、渲染标签【显示模式】与手机【显示】抽屉都读 `uiStore.displayModeOf()`，写 `uiStore.setDisplayMode()`；热图值背后的 `fitCheck` / `strainCheck` 只是两个一次性的叠加开关，不持久化（06 §5.1）。
- 选热图会关掉另一个热图，并把 `renderMode` 从 `raytraced` 复位到 `shaded`：路径追踪会隐藏 `MeshBasicMaterial` 的热图叠加网格（§5.2 的模式表）。

### 5.3 模式切换

```typescript
export async function setRendererMode(ctx: RendererContext, mode: RenderMode): Promise<void> {
  ctx.renderMode = mode;
  if (mode !== 'raytraced' || ctx.rayTracer || ctx.disposed) return;
  // 首次选择先建实例再画两帧验证内核；期间光栅化继续可用。
}
```

懒创建的 Promise 存在 `ctx.rayTracerLoading`，两个调用方共享同一次创建；如果期间它被换掉（恢复逻辑或重试），刚建好的实例归发起方释放。

实例建好后先做首帧验证：在当前场景上连画 `VERIFY_FRAMES = 2` 帧（第一次调用只记下场景变化，第二次才把内核发出去），再由 `verifyRayTracing()` 判定这台设备是否支持路径追踪：

- `GPUDevice` 上挂一个 `uncapturederror` 监听器，任何消息都算 `failure: 'gpu-error'`，原文进 `detail`。WebGPU 的着色器编译与绑定组错误异步上报，JS 调用不会抛；`device.lost` 也一并监听，掉上下文同样算 `gpu-error`。
- `device.queue.onSubmittedWorkDone()` 把队列排空后再收集错误（浏览器没有这个调用就跳过这一步，不因此判定设备失败）；超过 `VERIFY_TIMEOUT_MS = 30000` 未排空才算 `gpu-error`。
- 排空后调 `tracer.measureSampleAverage()`（直通 `WebGPUPathTracer.getSampleCountsAsync()`，不走那个 60 ms / 250 ms 的节流回读），把数值写进 `detail` 一起显示，但不参与判定。
- 判定前先看窗格尺寸：CSS 尺寸小于 `VERIFY_MIN_SIZE = 16` 时返回 `null`，表示当前无法判定，`ctx.rayCapability` 保持空着、下次切换再试。被布局隐藏的窗格尺寸被限制为 1×1，六个 wavefront 内核全部 `cannot index type 'RayData'` 解析失败。

结论存在 `ctx.rayCapability`，一个视口只测一次；失败时销毁刚建好的实例并抛 `RayTracingUnsupportedError(failure, detail)`，交给 §5.4 的恢复逻辑。

> **注**：验证复用要画的那几帧，不另搭最小场景。只有异步错误、上下文丢失与排空超时会把光追关掉，回读与样本计数只写进 `detail`。

### 5.4 光追失败的处理

运行期异常统一走 `ui/viewport3D/engineSync.ts` 的 `recoverWithRaster()`（`Viewport3D` 初始化失败也调用它），四个触发点：初始化时的 `setRendererMode`、渲染循环里的 `renderScene`、显示模式订阅、光追配置订阅。

- 它销毁光追实例，把 `ctx.renderMode` 与 UI store 复位成光栅化。
- 探测被拒时提示【本机 WebGPU 跑不了光线追踪（GPU 报出 WebGPU 错误 / 内核未产生采样 / 内核初始化失败）：<detail>。已切回光栅化模式。】，其余异常提示【光线追踪运行失败，已切回光栅化模式。】
- 探测结论同时经 `noteRayTracingUnsupported()` 写进 `perfStore.rayUnsupported3D`，三处显示模式入口据此把【光线追踪】置灰并在悬停/副标题里带上原因（06 §5.1）。
- 非光追模式的异常继续向外抛。

## 6. 光线追踪

`render/renderer/rayTracingRenderer.ts` 把 `three-gpu-pathtracer/webgpu` 的 wavefront 路径追踪器接到现有场景上。

> **说明**：它不克隆第二套布料或模特网格，以当前 `Scene` 为唯一数据源。

光追按帧累积样本：累积分辨率与每帧路径数决定铺开速度，场景与相机的变动决定何时重启累积，累积初期由光栅帧垫底，收敛到上限后降噪。

### 6.1 构造时的四个开关

```typescript
tracer.synchronizeRenderSize = false;   // 尺寸由 syncRenderSize() 自己管（§6.2）
tracer.renderDelay = 0;                 // 关掉自带的低分辨率预览
tracer.minSamples = 0;
tracer.fadeDuration = 0;                // 首帧即全不透明，不退到未清除的绘制缓冲
```

- 低分辨率预览调 `PathTracerBackend.setSize()` 会清空累积缓冲，故关掉预览。
- `minSamples = 0` 使 `autoClear` 始终为真；`alpha: false` 且没有 `preserveDrawingBuffer`，缓冲内容不确定。
- 因此只有一个累积分辨率，且总是全分辨率。

### 6.2 尺寸与路径预算

`syncRenderSize()` 每帧按 `renderer.getSize()`（CSS 尺寸，不含 devicePixelRatio）乘 `renderScale` 调 `tracer.setSize()`，并把 `frameBudget` 抬到至少宽×高。库内部槽位数学：

- wavefront 的路径槽池等于 `min(frameBudget, 像素数, MAX_RAY_DATA_COUNT)`，而 `MAX_RAY_DATA_COUNT` 由写死的 128 MB 缓冲上限算出，约 59.9 万条。
- 若按 DPR=2 的绘制缓冲累积，1600×1000 的窗格是 640 万像素，槽位只够 9% 的像素；`PopulatePixelIndicesKernel` 按像素序号发放，先照亮的是顶部区域。
- 按 CSS 尺寸并把预算提高到像素数后，覆盖全部像素只需个位数帧；更大的窗格可能超过槽池上限，用【渲染比例】把像素数限制到 60 万以内即可一帧覆盖。

### 6.3 静止判定与签名同步

`render()` 返回布尔值：`false` 表示这一帧没有光追画面，由 `renderScene()` 立刻画一帧光栅顶上去。

#### 6.3.1 场景签名与静止判定

```
每帧比较三个场景签名 + 相机变化量：
  topologyKey  受支持 Mesh 的 uuid、几何 attribute version、material 集合、有效可见性
  materialKey  uuid 与 version
  transformKey 受支持 Mesh 的世界矩阵
  cameraDistance(cameraValues, lastCameraValues)

双阈值滞回决定 viewMoving：
  正在光追 → 变化量超过 VIEW_SETTLE_TOLERANCE(1e-4) 算「又开始动」
  正在光栅 → 变化量超过 VIEW_MOVE_TOLERANCE(2e-3) 才算「在动」

在动的帧只记账，不同步也不采样；静止的下一帧一次性交给追踪器
（setScene / updateCamera / updateMaterials / updateTransforms / updateLights / updateEnvironment）
并当场 renderSample()，不设任何静止计时。

累积重启另有阈值：与上次同步相机位置的最大逐元素差超过 CAMERA_RESTART_TOLERANCE(2e-3)
才调 updateCamera()，否则保持累积。
```

#### 6.3.2 BVH 与同步窗口的临时替换

- 拓扑同步时若布料位置或法线 version 改变，先对路径追踪器挂在 `BufferGeometry.boundsTree` 上的 BVH 调 `refit()`；索引缓冲被替换则删掉旧 BVH，让 `setScene()` 重建。
- `withPathTracingScene()` 在同步窗口里做两件临时事：舞台地面换成 `MeshStandardMaterial` 替身；选中高亮、PIN 小球等 Basic/Normal 辅助网格临时隐藏。`three-gpu-pathtracer` 只接受 Standard/Physical 材质，回调结束后恢复原状态。
- 投影在透视与正交之间切换时 `rebindCamera()` 把拓扑键置为 `CAMERA_SWAP_KEY`，触发一次完整重采集。

> **注**：布料每帧变形都会刷新 BVH 并重启渐进采样。被临时隐藏的辅助对象只在过渡的光栅帧里出现，光追画面上看不到选中高亮与 PIN 小球。

### 6.4 早期样本的光栅垫底

光追 pass 刚开始的几十个样本尚未铺开，降噪也不执行，`drawRasterOverlay()` 在 `blendWeight < 1` 的这些帧里多做一次离屏绘制：

把当前 Scene 用光栅管线画进 `blendTarget`（半浮点、绘制缓冲尺寸、不含 tone mapping 的线性 HDR），再以 `1 - blendWeight` 的不透明度把这块全屏四边形叠在刚呈现的光追图之上，得到 `mix(光栅, 光追, blendWeight)`。

#### 6.4.1 四边形的 UV 翻转

四边形不用 `map` 而是 `colorNode = texture(base, uv().flipY())`：

WebGPU 上渲染目标的第一行在顶部，而全屏四边形顶边的 `uv().y` 是 1，不翻 v 会上下颠倒；`TextureNode` 的自动翻转要等 `builder.isFlipY()`，那在 WebGPU 后端恒为 false。

#### 6.4.2 混合权重与中断

`blendWeight = 实测每像素样本数 / min(RASTER_BLEND_SAMPLES = 32, maxSamples)`，达到后覆盖层不再绘制，画面是纯光追结果；权重来自 `measuredSamples`，因此中断时（`restartSampling()`）会一并归零、从光栅重新开始。

### 6.5 采样读数

`render()` 末尾的 `readSampleCount(now)` 做节流回读：

混合未完成时间隔 `BLEND_READBACK_MS`（60 ms）让过渡平滑，之后按 `SAMPLE_READBACK_MS`（250 ms）调 `WebGPUPathTracer.getSampleCountsAsync()`，取每像素平均采样数存进 `measuredSamples`，`sampleCount` 读它并夹到 `maxSamples`。

每次中断都递增 `sampleGeneration`，回包时代际不符就丢弃。

> **注**：帧数与样本数不同量级：wavefront 后端一次 `renderSample()` 只推进一个 bounce，一个像素累积到一个样本要跨若干帧。时间轴左端 `SPP:` / `Cost:` 读数显示这个值与累积到该值所用的时间（分母为【最大采样数】，06 §5.4）。

样本数为 0 时，`render()` 记下它是被哪一道挡下的：

```typescript
tracer.deferReason;  // 'deforming'（场景签名变了） | 'moving'（相机在动） | null
tracer.isBlending;   // 光栅垫底还没退场
```

`rayTraceState(ctx)`（`rendererContext.ts`）把它和模式、验证结论汇成一个值：`'inactive' | 'building' | 'deforming' | 'moving' | 'blending' | 'traced' | 'unsupported'`。

`EngineSync` 每帧 `noteRayTraceState()`，值一变就落进 `perfStore.rayState3D`。

`SPP` 分子为 0 时时间轴与手机顶栏在读数后追加短码（【光追内核加载中】 / 【布料每帧在变】 / 【视角未静止】 / 【光栅过渡中】 / 【本机不支持】，文案表在 `ui/optionTables.ts`），桌面视口左上角角标同样用它替下固定的【渐进采样】。

### 6.6 参数链路

工程字段 `scene.render.rayTracing` 是唯一来源，缺省或越界由 `normalizeRayTracing()` 收敛。链路分四层：

```
1 渲染标签滑条 → ui/sceneCommands.ts 的 setRayTracingConfig(label, patch)
                 （patchValue：可撤销、写进 `scene.render.rayTracing`）
2 EngineSync 订阅：比较 JSON.stringify(normalizeRayTracing(...)) 签名；renderMode 变化也会重新下发
                 → 更新 ctx.rayConfig，再调 rendererContext.ts 的 setRayTracingConfig(ctx, config)
3 该函数只在 renderMode === 'raytraced' 且 ctx.rayTracer 已就绪时转发，否则只留在 ctx.rayConfig 等懒初始化
4 RayTracingRenderer.setConfig()：六个数值直接映射到 WebGPUPathTracer 同名属性
                 （maxBounces / maxSamples / renderScale / filterGlossyFactor /
                   clampDirect / clampIndirect）→ 处理降噪 → tracer.reset()
                 frameBudget 不在这里赋值：由 syncRenderSize() 每帧取
                 max(配置值, 累积分辨率像素数) 写入（§6.2）
```

- `ctx.rayConfig` 另存一份，光追实例首次创建时即写入工程参数。
- 参数一改就从零重新累积。
- 透明层数（`maxTransparentBounces`）与低分辨率预览参数（`lowResScale` 等，§6.1 已关掉预览）没有界面入口；火噪没有专项控制，能调的只有 `clampDirect` / `clampIndirect` 两个钳制值。

### 6.7 降噪

走 `three-gpu-pathtracer` 的 `OIDNDenoiser` 加 `oidn-webgpu`：

- 权重打包在 `assets/weights`（Apache-2.0，署名见 `assets/weights/ATTRIBUTION.md`），运行期不联网下载。
- 首次需要时按 `denoiseModel` 经 `bundledAssetUrl()` 取 `/weights/rt_hdr_alb_nrm[_small].tza`（引导模型）与 `/weights/rt_hdr.tza`（颜色模型）；本地开发走站内路径，站点构建走 Function。每个模型只创建一次，缓存在 `denoisers` 表里。
- 路径追踪器只在累积到 `maxSamples`、渲染停止之后才执行降噪，【最大采样数】即降噪触发点；界面与 `normalizeRayTracing()` 都把它夹在 8~1024，`maxSamples = 0` 在本应用不可达。
- `guardDenoiser()` 用 Proxy 包住 `update` / `denoise`：读取、编译或运行期报错都只记一条 console 警告，把失败的模型记进 `failedDenoiseModel`，摘掉 denoiser 并通过 `uiStore.showToast` 提示，光追继续输出未降噪画面。
- `setConfig()` 是异步的而渲染循环是同步的：等待权重期间 `render()` 照常累积，denoiser 挂上后由下一次 `reset()` 生效。
- 换权重文件只能从上游的 LFS 原始地址取：`https://media.githubusercontent.com/media/RenderKit/oidn-weights/master/<file>`。

> **注**：`failedDenoiseModel` 记当前加载失败的模型；关闭降噪时由 `setConfig()` 清空，开启时仅当所选模型与失败模型不同才重新加载权重，关掉再打开（或换模型）即可重试。GitHub 的 RAW 视图与 jsDelivr 返回 132 字节的 LFS 指针而非二进制，`initUNetFromURL` 会失败。

## 7. 相机与拾取

两台相机与投影直接挂在上下文上，预设与取景共享一份方向表，拾取以表面射线优先。

### 7.1 双相机与投影

- 透视与正交是同一视口上的两台相机，`ctx.camera` 指向生效的那台：`setCameraProjection(ctx, projection)` 交接位置、朝向与 `controls.object`，并按当前朝向重取景。
- 正交视野高度存 `ctx.orthoViewHeight`，滚轮缩放走相机 `zoom`。
- 缩放方向统一为向下靠近、向上远离，滚轮与中键拖动一致。`OrbitControls` 两者都是反的且没有开关，因此由 `attachZoomGestures()` 接管：滚轮在窗口捕获阶段监听并 `stopPropagation()`，早于控件挂在 canvas 上的自家监听；中键拖动把 `mouseButtons.MIDDLE` 置空后按 `clientY` 增量自行推拉。
- 两个手势都调 `dollyIn()` / `dollyOut()`，正交相机由此改 `zoom`；监听随 `disposeRendererContext()` 解绑。
- 机位、目标、视野与投影都落在 `scene.camera`，随工程保存、打开时恢复；界面偏好只记住投影的默认值，供没有相机记录的工程使用（02 §8）。

```typescript
const camera = new THREE.PerspectiveCamera(45, width / height, 0.1, 100);
camera.position.set(0, 1.4, 3.2);
controls.enableDamping = true;
controls.dampingFactor = 0.08;
controls.target.set(0, 0.9, 0);   // 对准模特中心
```

### 7.2 视角预设与取景

`ClothPicker.applyPreset()`（`core/engine/clothPicker.ts`）走 `cameraFit.ts` 的 `CAMERA_VIEW_FRAMES`：

- 六个正位（正视/后视/左视/右视/仰视/俯视）加四个 45° 侧位（正左/正右/后左/后右），快捷键是小键盘 `2 8 4 6 0 5` 与 `1 3 7 9`。
- 取景范围取布料、模特与可见参考物的合并 AABB，按当前视口宽高比与视野角算出刚好框住全部对象的距离（`fitCameraToBox()`）；首次加载停在正视。
- 俯视与仰视改用 ±Z 作为 up 向量。
- `frameScene()` 只改距离不改朝向。

> **注**：双击 3D 空白处是选中版片或清空选择，相机本身不参与【适应视图】；`F` 只作用于 2D 制版视图。

### 7.3 粒子拾取

`pickClothParticleAtScreen()` 三步，顺序不可交换：

```
1 对合并布料网格做一次表面射线检测（three 的 `Raycaster`）
2 命中 → 命中点转局部坐标，由 trianglePanelIds 求出所属片 → pickNearestAtPoint(point, radius, panelSlot)
         在该点周围做球形查询并限定同片，取三维距离最近的粒子
         球形查询无结果 → 退回命中三角形的角点最近者
3 表面完全没命中 → pickNearestParticle() 的屏幕容差垂距搜索
```

> **注**：单靠垂距搜索不看深度也不看遮挡，射线穿过前片会打到内侧或后片的粒子，因此第 3 步只是后备方案。

拾取的 `pointerdown` 监听挂在容器上并以捕获阶段注册，先于 `OrbitControls` 的 canvas 监听，从而只在打 PIN、拔 PIN 与捏布拖拽的按下上 `stopPropagation()`（`ui/viewport3D/useClothPicking.ts`）。悬停判定与修饰键规则见 06 §5.2。

## 8. 性能策略

渲染层的开销集中在四类：绘制幅度由像素比上限与隐藏窗格跳过绘制控制（§1.1、§1.2）；几何与材质改动由关闭视锥剔除、动态顶点缓冲和三签名比较避免整份重建（§2.1、§3.3）；外部资源按需要加载与复用（§4.2、§4.3、§5.3）；光追只在场景签名变化时同步资源，到达 `maxSamples` 后停止累积（§6.3、§6.5）。

3D 视口的悬停判定按帧合并：`pointermove` 只登记指针位置，`requestAnimationFrame` 里最多算一次，内容是一次布料射线加一次身体球迹步进；指针静止时只在工具、播放状态或 PIN 集合变化时重算。
